# Airport proximity check-in

Fly Washington uses core 0.8.0's production Check in shortcut beside Explore / My passport. Airport details has one Record a visit / Add another visit button, opening a choice between Check in here and Add a manual visit. The chooser never requests location automatically. Both entry points use the same modal date/notes form after airport selection; editing stays in Visit history. Secondary actions have a visible surface and border without hovering, plus hover and keyboard focus feedback. The temporary sample UI is removed; no query parameter is required. Core owns location acquisition, UI, evidence, migrations and tests. Washington owns airport coordinates and the checkIn configuration in src/program/program.ts.

Initial policy: 1.5 **statute** miles (2414.016 metres) around each airport reference point, maximum reported accuracy 200 m, maximum reading age 30 seconds, 30-second acquisition deadline, and America/Los_Angeles for the captured visit date. Distance plus reported accuracy must fit in the radius. Airports may override checkInRadiusMeters. These are initial configurable values awaiting real-airport acceptance; they are not surveyed stamp locations or a guarantee of accuracy. Radius overlaps require user selection, never automatic multi-airport credit.

The owner approved airport-level proximity because the same airport stamp may be available at several FBOs. This supersedes the earlier precise-stamp-target requirement in DATA-SOURCES.md and core Planning.md. Current reference coordinates are used at airport scale; source stamp instructions are unchanged. Review unusual/large airports and seaplane bases in physical acceptance. GPS is not official passport validation and does not change award rules or existing stamp-collection choices.

First-use Check in explains local evidence and export inclusion before requesting location. Later user-initiated check-ins reuse any valid permission grant; browsers may ask again. There is no launch-time or continuous tracking. Cancelling, hiding the page, completion or timeout stops acquisition. Manual search and date-only saving are available when location is unavailable, denied, inaccurate or outside range. Saving a location-assisted visit records the acquisition time, not the later save time. Notes edits preserve evidence; date edits explicitly remove it. Backups now use schema 4 and older exports remain importable. Database v4 prevents older writers from dropping evidence; keep an export before device testing and use the updated app after migration.

## Test locally

The rebuilt port 5173 preview contains the real feature. Desktop localhost can request location, but a desktop reading may be too imprecise or outside all airport ranges. Ordinary http://192.168...:5173 phone access cannot provide secure geolocation; use a trusted HTTPS development endpoint or deployed HTTPS build for physical GPS testing. Do not interpret the HTTP fallback message as a device GPS failure.

Check iOS Safari, Chrome and the installed Home Screen app separately. Android Chrome/PWA also requires acceptance when a device is available. Cover online/airplane mode, initial/repeated/denied permission, hiding during acquisition, cancellation, weak/approximate location, multiple airports in range, repeat same-day warnings, timezone/day boundaries, manual fallback, reload and export/import. Browser simulation validates app logic; it does not validate reception, permission duration or reference-point coverage. PWA installation is not a promise of permanent permission.

Primary API documentation: [W3C Geolocation](https://www.w3.org/TR/geolocation/), [Chrome secure-context requirement](https://developer.chrome.com/blog/geolocation-on-secure-contexts-only). The detailed reusable contract is passport-core/docs/GPS-CHECK-IN.md.

## Automated validation note

Windows Playwright WebKit 2359 returned injected position timestamps in epoch microseconds (1000 times the millisecond API value). The integration test conditionally corrects that simulator output; production does not normalize invalid timestamps. Chromium uses its native location simulation without this correction. A passing WebKit test therefore establishes the UI/save flow with simulated standards-shaped evidence, not real iOS location acquisition. Physical iPhone/PWA acceptance remains required.
